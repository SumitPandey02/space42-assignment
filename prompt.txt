# Space42 Senior QA Automation Assessment

## Playwright + TypeScript | GitHub Actions | Allure Reports

## 1. Your role and objective

Act as a Senior SDET, QA Automation Architect, and TypeScript engineer.

Build a complete, maintainable, resilient API automation framework for the attached Space42 Senior Engineer – Technology Quality Assurance assessment.

**Mandatory technology stack:**

* Language: TypeScript
* Test framework and API client: Playwright Test and Playwright APIRequestContext
* Runtime: Node.js
* Package manager: npm
* CI/CD: GitHub Actions
* Test reporting: Allure Reports
* Version control: Git and GitHub
* Validation: TypeScript types and Zod or an equivalent runtime schema validation library

Target API: https://restful-booker.herokuapp.com

Do not replace this stack with Python, Java, Selenium, Cypress, or another test framework.

The objective is to deliver an executable project that demonstrates senior-level API automation skills, including authentication lifecycle management, complex booking state validation, idempotency, concurrency, safe retry handling, environment isolation, and useful CI reporting.

The implementation must be understandable enough for me to explain every major design decision in a technical interview without AI assistance.

## 4. Playwright and TypeScript requirements

Use Playwright Test as the test runner and `APIRequestContext` for HTTP API operations.

Configure `playwright.config.ts` with:

* A configurable API base URL.
* TypeScript-compatible test discovery.
* Sensible test and assertion timeouts.
* Retry settings appropriate for local versus CI execution.
* Worker count configurable through environment variables.
* Allure reporting.
* Trace or diagnostic collection on failure where applicable.
* Environment-specific settings without hardcoded secrets.

Create typed API client methods for authentication and booking operations.

Use appropriate HTTP methods and explicit response assertions.

Use Playwright's built-in API request support rather than introducing Axios or another HTTP client without a compelling reason.

Use Zod or an equivalent runtime validator to validate response bodies. TypeScript types alone do not validate untrusted JSON at runtime.

Keep request payloads and response models strongly typed.

Use `async`/`await` consistently and handle errors explicitly.

## 5. Authentication and token lifecycle management

Implement a reusable TypeScript authentication manager.

Requirements:

1. Generate tokens dynamically through the supported POST `/auth` endpoint.
2. Cache tokens appropriately.
3. Track token acquisition time and use a configurable refresh threshold if the service does not expose token expiry.
4. Handle a 401 response by invalidating stale authentication state and refreshing the token when a retry is safe.
5. Handle 403 separately because it may indicate an authorization failure that refreshing the token will not fix.
6. Implement a single-flight refresh mechanism so concurrent calls in the same JavaScript execution context await the same in-progress token refresh.
7. Ensure that refresh failures do not leave a permanently rejected promise or stale token.
8. Test cached-token reuse, concurrent refresh, refresh failure, and unauthorized-response handling.
9. Avoid repeatedly refreshing authentication for every test unnecessarily.

Important limitations:

* An in-memory promise lock coordinates only callers that share the same manager instance in the same runtime.
* It does not coordinate separate Playwright workers or GitHub Actions jobs.
* If cross-process coordination is genuinely needed, document the design and implement it only where justified.
* Do not invent an authentication token expiry timestamp if the API does not provide one.

Use controlled mocks or test doubles to simulate expiry and unauthorized responses. Do not deliberately destabilize the public sandbox to prove the refresh implementation works.

## 6. Booking lifecycle and schema validation

Implement an end-to-end API lifecycle using dynamically generated, isolated test data:

1. Verify API availability using the documented health-check endpoint.
2. Authenticate.
3. Create a booking.
4. Validate the response status, booking ID, payload structure, and returned fields.
5. Retrieve the booking by ID.
6. Verify its persisted state.
7. Update the booking using PUT.
8. Verify the full updated state.
9. Apply a partial PATCH.
10. Verify the modified field and preserved fields.
11. Delete the booking if the test owns it.
12. Verify the expected post-deletion state.

Use date helpers to generate valid check-in and check-out dates.

Validate the following invariants:

* Valid date formats.
* Checkout strictly later than check-in.
* Correct nested `bookingdates` structure.
* Numeric `totalprice`.
* Boolean `depositpaid`.
* Valid string fields for names.
* Required fields present.
* Response data consistent with the request and documented API behaviour.

Do not hardcode dates that become invalid over time.

### Overlapping booking scenario

The assessment asks for an attempt to create overlapping bookings for the same room/date range using a second user context.

First verify the target API's actual capabilities. Restful Booker may allow independent booking records without enforcing room-level overlap rules.

Implement the test so that it:

* Creates isolated synthetic test data.
* Attempts the specified duplicate or overlapping scenario.
* Records the actual status code and response.
* Validates documented behaviour instead of assuming a 400 or 409 must occur.
* Uses a deterministic mock-based test for an enterprise API that explicitly rejects overlapping reservations, if the sandbox cannot demonstrate that behaviour.

Clearly distinguish actual sandbox behaviour from the expected enterprise business rule.

## 7. Idempotency and retry safety

### Repeated PUT

Create a booking and send the exact same complete PUT payload three times.

After each request:

* Validate the response status and structure.
* Retrieve the booking.
* Compare the persisted state against the intended payload.
* Verify that unrelated fields are preserved.
* Report whether the operation is state-idempotent.

Do not invent resource versions or assert that version metadata remains stable if the API does not expose it.

### PATCH drift

Create a booking and save its original state.

Update only `totalprice` through PATCH.

Retrieve the booking and verify that:

* `totalprice` reflects the intended update.
* `firstname` and `lastname` remain unchanged.
* `bookingdates` remains unchanged.
* `depositpaid` and other unmodified fields remain unchanged.

### Retry utility

Implement a reusable retry utility with:

* Configurable retry count.
* Exponential backoff.
* Bounded delays.
* Optional jitter.
* Explicit handling of transient network failures and retryable server responses.
* Clear retry diagnostics.

Do not automatically retry non-idempotent POST operations after ambiguous network timeouts. The initial request might already have succeeded.

Implement reconciliation or safe recovery where possible. Do not claim that the API supports idempotency keys unless verified.

## 8. Concurrency and race-condition tests

Use TypeScript asynchronous execution and coordinated request dispatch to test two conflicting updates to the same booking ID.

Requirements:

1. Create a booking specifically for the test.
2. Capture the original state.
3. Prepare two valid, conflicting PUT or PATCH payloads.
4. Coordinate the workers using a synchronization barrier or equivalent mechanism.
5. Dispatch both requests concurrently.
6. Record status codes, request start times, completion times, and responses.
7. Retrieve the final state.
8. Verify the response schema and data integrity.
9. Determine the observed outcome: last-write-wins, optimistic-lock rejection, or another supported behaviour.
10. Repeat a limited number of times if safe.

Do not claim that requests were sent at precisely the same millisecond unless the implementation can substantiate it.

Do not assume Restful Booker supports optimistic locking or resource versions.

Use deterministic mock-based tests to verify specific enterprise behaviours, such as 409 conflict responses, where the public sandbox cannot guarantee them.

Keep real sandbox observations, mocked behaviour, and enterprise expectations separate in the documentation and Allure results.

## 9. Shared sandbox resilience and cleanup

The framework must tolerate other users modifying or deleting bookings.

Implement:

* Unique test data.
* Test-owned booking IDs.
* Safe cleanup in `finally` blocks or equivalent teardown.
* Context-sensitive handling of 404 responses.
* Controlled recovery for missing prerequisites.
* Bounded retries for transient failures.
* Clear diagnostics when recovery is exhausted.
* Isolation between parallel tests.
* Cleanup only for records created by the current test.
* No uncontrolled deletion of existing bookings.

Do not automatically recreate a booking during a test that is explicitly verifying deletion.

Do not globally suppress 404 responses.

Use Playwright fixtures or hooks to manage setup and teardown consistently.

## 11. GitHub Actions CI/CD

Create `.github/workflows/api-tests.yml`.

Use GitHub Actions to execute the framework on pushes and pull requests. Include a manual `workflow_dispatch` trigger.

Use a currently supported Node.js LTS version compatible with the project's dependencies. Pin actions to stable, explicitly selected versions rather than using floating `latest` tags.

### Workflow steps

1. Check out the repository.
2. Set up the chosen Node.js version.
3. Enable npm caching.
4. Install dependencies reproducibly using `npm ci`.
5. Run formatting or lint checks.
6. Run TypeScript type checks.
7. Run deterministic unit and mocked tests.
8. Run API integration tests against the configured sandbox.
9. Generate Allure result files.
10. Upload Allure result files as GitHub Actions artifacts even when tests fail.
11. Generate the HTML Allure report when possible.
12. Upload the generated HTML report as an artifact, even when the test job fails after results are produced.
13. Preserve the original test failure status; report generation or artifact-upload steps must not accidentally turn failed tests into a green pipeline.

Use separate CI stages or jobs where this improves clarity and avoids unnecessary sandbox traffic.

### CI resilience

* Configure `BASE_URL` through an environment variable.
* Do not hardcode API credentials.
* Use GitHub Secrets only when real secrets are needed.
* The public demo API may not require repository secrets for its standard examples.
* Use bounded retries and timeouts.
* Avoid excessive parallel requests to the public sandbox.
* Keep deterministic unit and mock-based tests independent of external network availability.
* Treat sandbox outages and service instability as visible integration failures, not as proof of application defects.
* Do not automatically mark failed tests as successful simply because they are flaky.
* Preserve Allure evidence for diagnosis.

### Artifact retention

Configure sensible artifact retention for:

* Allure raw results.
* Allure HTML report.
* Any additional Playwright diagnostic artifacts required for debugging.

Use clear artifact names that distinguish branch, commit, and execution where feasible.

### GitHub Pages

Do not publish reports publicly by default. First implement private-by-default artifact storage.

If GitHub Pages publication is useful, document it as an optional feature requiring explicit configuration and appropriate repository permissions. Do not expose test evidence or sensitive information publicly.
